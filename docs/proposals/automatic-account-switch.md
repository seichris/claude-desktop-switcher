# Claudeの作業完了を待つ自動起動

状態：利用者がAccessibilityを使う自動終了・再起動、作業を中断しないこと、強制終了しないことを承認済み。実装後の独立レビューで安全性の未解決条件を発見したため、通常終了要求を無効化し、未マージ・未インストールで保持する。

## マージを止める未解決条件

検証したClaude2.42304.0では、主WebViewの読み込み完了または60秒のタイムアウトを待ったあとに、CodeとCoworkの管理機構を読み込んで終了ガードを登録する。macOSの起動完了と5秒の待機では、この登録を証明できない。Chromium152.0.7977.149の`AXLoaded`もブラウザ側の読み込み完了通知・Claude側の登録より早く真になる。非空のカスタムDockメニューは登録後に作られるが、Dock側のAX表示が現在のClaudeプロセスから返された内容であるという公開された鮮度保証はない。

現行の実装は`require_guard_readiness`を`SafeQuit::prepare`と`request`の両方で確認し、必ず`automatic_guard_unverified`を返す。したがって動作中Claudeには終了要求を送らない。時間や見た目を根拠にこの拒否を外してはいけない。プロセスに結びついた登録完了の確認手段、または起動前から常に有効な公式の終了保護が必要である。これは未解決で、以下の自動動作は出荷済みの機能ではなく、利用者が合意した到達目標である。

### 調査の再現に使う根拠

- 参照した公式Claudeの`app.asar`はSHA256`bfa22ac393906762fa04b9607ff202907405b089c1ae7db257159202f31bb3d0`。主チャンク`index.chunk-muI2IV6k.js`の`So`は主WebViewを待ち、読み込み完了後またはタイムアウト後に`installQuitSessionGuard`を呼ぶ。`lQt`が`ZOn`を通じて終了インターセプターを設定する。起動時刻だけではこの呼び出しを証明できない。
- 同じチャンクのシグナルハンドラーは終了インターセプターを迂回する。`SIGTERM`を通常終了の代替にしてはいけない。
- 同梱Electron44.7.2の[アプリデリゲート](https://github.com/electron/electron/blob/v44.7.2/shell/browser/mac/electron_application_delegate.mm)はカスタムDockメニューをプロセス内に保持するが、外部のDock側のAX表示がそのプロセスから今返されたメニューであることまでは証明しない。
- 同梱Chromium152.0.7977.149の`AXLoaded`はレンダラーの読み込み状態を参照する。[Documentの読み込み完了処理](https://chromium.googlesource.com/chromium/src/+/152.0.7977.149/third_party/blink/renderer/core/dom/document.cc)は、ブラウザへの完了通知より先に状態を完了へ変更する。さらに`So`は100ミリ秒のタイマーで監視を開始するため、AXの完了をそのまま終了保護の登録完了と解釈してはいけない。

### 検証結果

PR：[#5](https://github.com/seichris/claude-desktop-switcher/pull/5)、ソースレビュー対象：`85c4317..8593cda`。198個のworkspaceテスト、workspace build、clippy、fmt、JavaScript構文、日英の600・720ピクセル幅の表示検査を実行した。macOSランナーで通常の10枚と自動終了を拒否する画面の日英2枚を再生成し、画像を確認した。

独立したアーキテクチャとネイティブ経路のレビュー後、Codex Securityの差分スキャン`8c2350a0-1f7c-4cff-9d3b-02818ac972a5`で変更されたソース17ファイルを確認した。現在の拒否ゲートを迂回する到達可能な問題は見つからなかったが、終了保護の準備完了は未解決のままで、自動終了を有効にしてよいという結果ではない。後続の画像・ドキュメント更新は実行コードを変更していない。

実機ではClaudeのバックグラウンドタスクが残っていたため、終了・切り替え・インストールを行っていない。既存のインストールは`0.24.6-local.5`のままで、候補版を完成した機能として導入してはいけない。

## 対象と採用範囲

### 追加で承認された段階検証

利用者が段階的なテストの実行を承認した。既存のインストールと稼働中のClaudeは維持し、終了要求の拒否ゲートを弱めない。

- [x] インストール済みの検証対象アーカイブから必要な関数だけをメモリ内で取り出し、偽のタスクと決定的な時計で起動の競合を再現する。Claude本体、実データ、認証情報を変更しない。ベンダーコードをリポジトリへ複製しない。
- [ ] 使い捨てのネイティブアプリで、実際のAXツリー、既知の待機ボタン、未知のダイアログ、権限なし、プロセスの終了・置き換えを検証する。実アプリの許可を取り消して障害を作らない。既存の正規化・認識コードをテストから使い、製品の終了ガードを迂回できる設定を追加しない。
- [ ] プロセスに結びついた終了保護の準備完了を証明できた場合だけ、ほかの実作業の終了後に、既存のDesktopログインと使い捨てのCode作業で実機検証する。証明できなければ実施を止め、その条件を結果へ明記する。
- [ ] テストの一次結果を確認し、独立レビュー後にPRへ保存する。シミュレーション、実AX、実Claudeの証拠を混同しない。

判定基準は、保護の登録前には終了が安全であると判断できないこと、登録後の偽タスクでは応答・入力待ち・バックグラウンド処理が終わるまで待機すること、AXは正確な待機ボタン以外を押さないこと、未知の状態や権限・本人確認の変化では操作を止めることとする。テストの成功だけでは終了保護の準備完了を証明したことにしない。

#### 段階検証の実測

利用者はテスト用画面の修正後に調査を続けることを承認した。次の検査は、先に画面なしでライフサイクルを検査し、1回の明示実行に対して1ケース・1テスト用プロセス・1ダイアログだけを開く。表示と終了はそれぞれ1回だけ許可し、期限・終了要求・複数イベントが重なっても再実行しない。テストであると分かるアプリ名・アイコンを使い、失敗時に別ケースを自動起動しない。Claude本体には終了要求を送らず、未解決の準備完了条件を弱めない。

`node scripts/automatic-switch/startup-guard-test.mjs`は、固定したローカルアーカイブの関数をメモリ内で読み、偽のアプリ・管理機構・時計だけで16件を検査する。読み込みが遅い起動、100ミリ秒の監視前の空白、60秒のタイムアウト、応答・入力待ち・バックグラウンド処理、待機とキャンセル、重複要求、コールバックの解除を確認した。`--assert-five-second-readiness`は旧仮説を直接検査して終了コード1になる。実際のClaudeへ終了要求を送るテストではなく、実タスクがガードより先に開始できることや準備完了の証明までは主張しない。

追加の読み取り調査では、CodeのIPC登録は主画面の読み込みと終了ガードの登録より先に行われ、Code管理機構の読み込みやセッション開始にも登録完了を待つ依存を確認できなかった。タスク操作が可能であることも準備完了の証明に使えない。

使い捨てAppKitアプリによる実AXの初回検査は、期待したモーダルを取得できず失敗した。製品の認識処理が実機で動いたという証拠にはならない。検査中に利用者から終了・待機ダイアログが繰り返し現れるとの報告があったため、画面を開く検査を中止した。テスト用プロセスは終了を確認し、Claude本体のPIDとインストール済みSwitcherの版・バイナリハッシュは維持されていた。テスト用画面は製品と区別できる表示と、明示的に1回だけ開く手順が必要である。この失敗した実験は製品へ組み込まない。

初回の中止時点では、実AXでの待機選択・権限喪失・プロセス置換と、実Claudeでの終了・再起動は未検証だった。Claude本体へ通常の終了要求、強制終了、シグナル送信は行っておらず、Switcherも再インストールしていない。準備完了を確認できないためPRはDraftのまま保持する。

#### テスト用画面の修正後の実測

画面なしのSwift検査で、旧来の無制限な呼び出しが100回の表示を許して失敗することを確認した。共通の状態機械へ変更し、表示・待機選択・終了を各1回に制限した。終了後のコールバックはキャンセル操作として記録しない。ネイティブ検査は無視指定のテストとし、ケースの明示がなければ起動しない。非公開のロックで同時実行を拒否し、30秒以内の再実行も画面を開く前に拒否する。テスト用アプリは大きなTESTアイコンを表示し、20秒で自分のウィンドウを閉じて終了する。通常終了要求の繰り返しや強制終了は使わない。

実AXでの最初の失敗を再現した後、SDKにない`AXSheets`属性への依存を修正した。ウィンドウの直下の子要素の種類とPIDだけを確認して`AXSheet`を選び、会話の文字列や子孫を読まない。修正後、英語と日本語のネイティブシートで、正確な待機ボタン、偽タスクの保留、1回の表示・終了、異なるPIDと終了済み要素の拒否を確認した。未知のシートはボタンを押さず1回だけ閉じた。実際の画面でもTEST表示を確認した。即時の再実行はクールダウンで拒否され、画面を開かなかった。

別の画面なしアプリでは、既存の許可を変更せず、Accessibilityが許可されていないことを実測した。待機中の状態をテスト内で構成して`poll`が権限不足で止まること、`request`も準備完了の拒否を維持することを確認した。これは実際の許可の取り消しや、実Claudeでのプロセス置換を実行した証拠ではない。それらと実Claudeの終了・再起動は引き続き未検証である。

準備完了の追加調査では、ログ出力はファイルへのWinston転送であり、PIDに結びつくOSの準備完了通知は確認できなかった。ガード登録後の公開IPCにも確認用の取得操作はなく、ネイティブのサービス更新はシステムのサービス情報を更新するだけだった。安全な登録完了の証明には使えず、製品の拒否ゲートを維持する。

Codex Securityの差分スキャン`7e310aaa-68ab-4e46-b1d0-dffdfe0a1b63`は、`01b397b..bc77e70`のソース5ファイルとアーキテクチャを確認し、到達可能なセキュリティ問題は見つからなかった。一方、テスト用ロックの取得前に読んだメタデータで待ち時間を判定する競合を正しさの問題として記録した。ロック取得中にメタデータを読み直すよう修正し、別の実行が直前に時刻を書いた場合も画面を開かず拒否することを、画面なしの決定的な検査でREDからGREENへ確認した。製品のAX読み取り範囲と準備完了の拒否は、この追加修正では変更しない。

競合の修正後にfmt、workspaceのclippyとbuild、199件のworkspaceテストが成功した。3件の内部・実機テストは通常の実行から除外し、上記の個別実行と区別する。追加修正の独立レビューでも、競合の解消と製品の拒否を維持していることを確認した。

設定を共有する環境をGUIから順番に使う利用者を対象に、手動の終了手順を自動化する。軽い手順案内では毎回の操作が残るため、利用者が求めたネイティブAccessibility連携を採用する。CLIの終了確認は変更しない。

## 合意した動作

- GUIとトレイの起動操作を同じ処理に通し、重複した予約を拒否する。
- 起動中のClaudeがなければ、既存の同期・起動処理を使う。
- 起動中のClaudeが1つの場合だけ、管理対象、起動時刻、署名、検証済みのClaudeビルド、自動化可能な起動経路を検証する。
- 自動化可能な起動は、更新後のSwitcherが特別なバックグラウンド起動モードを無効にして作った新しいプロセスに限る。PIDだけを本人確認に使わない。
- 通常の終了要求を1回送り、Claude自身の作業中ダイアログで正確に一致する「Claudeを待つ」だけを選ぶ。CodeとCoworkの実際の稼働状態はClaude自身の判定に委ねる。
- タスク、入力待ち、バックグラウンド処理が残る間は待つ。CPU使用率、ファイルの古さ、子プロセスの有無から完了を推測しない。
- 元のプロセスが実際に終了したあとだけ、全Claude終了の既存ガードで再検証し、ローカルCode同期と選択環境の起動を実施する。
- 強制終了、OSシグナル、終了の繰り返し、Claudeの改変、非公開APIを使わない。
- 権限不足、未知のダイアログ、未検証ビルド、複数プロセス、管理外の起動、本人確認の変化では止まり、利用者に手動終了を案内する。保護を弱める回避操作は設けない。
- 待機中は対象と状態を表示する。Switcherを終了すると自動再起動は行わないが、Claude側で予約済みの終了は残る可能性があるため、取り消せると誤認させるボタンは置かない。

## プライバシー境界

Accessibilityは明示的な起動操作の間だけ、対象Claudeのネイティブ終了ダイアログに使う。主WebViewの会話や他アプリの画面を走査しない。許可を求める操作をUIに設け、設定画面の起動だけでOSの権限ダイアログを出さない。

認証情報、Keychain、Cookie、ブラウザストレージ、プロセス環境を読まず、ネットワーク通信を追加しない。起動証明はSwitcherの非公開領域に保存し、リンク、過大入力、PID再利用を拒否する。個別の利用者名やアカウントを実装・資料に含めない。
